Append-Only Logs Meet
In-Memory Hash Indexes

LagerKV is a lightweight, durable key-value store written in Go from the ground up. It follows the Bitcask architecture: sequential append-only logs on disk, an in-memory hash table holding the location of every key, and exactly one disk seek to read any value.

Features

What is inside the engine

Six decisions do all the work: write sequentially, index in memory, verify everything, expire lazily, lock the directory, and let the operator choose how hard to fsync.

No. 01 — The Write Path

Append-Only Log

Every SET and DELETE is a sequential append to the tail of the active segment. Random disk I/O becomes a straight line, which means write throughput stops being a function of how large the database has grown.

No. 02

In-Memory Index

KeyDir holds the file ID, byte offset and length of every live key. A GET is one hash lookup and then one seek — nothing else touches the disk. A missing key never costs a read at all.

No. 03

CRC32 Checksums

Each record is stamped with an IEEE CRC32 on write and verified on every read and at startup, so bit rot fails loudly instead of quietly handing back a corrupted value.

No. 04

TTL Expiration

Keys carry an optional expiry. An expired key vanishes from lookups the instant its clock runs out, and is swept from disk the next time compaction runs.

No. 05

Process Locking

A single flock on the database directory guarantees one writer. A second process opening the same folder is refused before it can corrupt a byte.

No. 06

Fsync Strategies

Choose where the durability line sits: flush on every write for maximum safety, flush on a background interval for balance, or let the kernel buffer and take the throughput.

Architecture

How it works

Three paths through the engine: the append, the single-seek lookup, and the background compaction that reclaims space.

01

The append-only write path

A client write is processed in three sequential steps:

  1. 01Build the record. The pair is serialised into a binary entry carrying CRC32, timestamp, expiry, key size and value size.
  2. 02Append to the log. The entry is written straight to the tail of the active segment. No page is ever rewritten.
  3. 03Update the index. A reference mapping the key to its new file ID, offset and length lands in the in-memory hash table.

Write operation

client › SET("foo", "bar")

append

segment_2.log › [hdr][key][value]

update index

KeyDir › "foo" → {file: 2, off: 120, len: 3}
02

The single-seek read path

The location of every key is already in memory, so a lookup never scans:

  1. 01Search KeyDir. One O(1) hash lookup. If the key is absent we return not-found immediately — no disk read happens at all.
  2. 02Verify the TTL. If the entry has expired it is treated as deleted and dropped from the index.
  3. 03Seek once. The recorded file ID and offset are used to fetch the record in exactly one disk seek.

Read operation

client › GET("foo")

index lookup

KeyDir › hit · file 2, offset 120

single seek

segment_2.log @ 120 › "bar"
03

Garbage compaction

A background worker keeps the log from growing forever by rewriting only what is still alive:

  1. 01Scan the logs. Every inactive segment on disk is opened and walked in order.
  2. 02Filter dead entries. Records that were deleted, expired, or superseded by a newer write are skipped.
  3. 03Swap atomically. Live keys are rewritten into new segments and swapped in, reclaiming the space the dead records occupied.

Usage

Build and run it

macOS or Linux, Go 1.24 or newer. Compile the daemon and the client, start the server, then drive the store from the terminal.

Step 01

Compile the binaries

Build the server daemon and the interactive client.

# build the server and the client go build -o bin/lagerkvd ./cmd/lagerkvd go build -o bin/lagerkv ./cmd/lagerkv-cli

Step 02

Start the daemon

It binds to port 8080 and writes segments into ./data.

# start the background server ./bin/lagerkvd

Step 03

Drive it from the CLI

Set with a TTL, read back, list the live keys, inspect the engine.

# set a key with a 60 second TTL ./bin/lagerkv set username saipraveen --ttl 60s # read it back ./bin/lagerkv get username # list every live key ./bin/lagerkv list # engine statistics ./bin/lagerkv stats

Running the test suites: go test ./... -v -count=1
