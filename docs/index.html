Engine Features

Core principles built into the storage engine for efficiency, durability, and correctness.

Append-Only Log

Writes are sequentially appended to log segments, converting random disk I/O into lightning-fast sequential writes for high throughput.

In-Memory Index

A hash map index (KeyDir) tracks record offsets in memory. Reads perform an O(1) memory lookup to find the file offset, requiring exactly one disk seek.

CRC32 Checksums

Protects against bit rot and data corruption. Each record is verified with an IEEE CRC32 checksum on startup and subsequent disk reads.

TTL Expiration

Allows keys to expire dynamically. Expired keys are hidden from requests instantly and swept away automatically during log compaction.

Process locking

Ensures database directory safety. Uses flock-based exclusive locking on startup to prevent data corruption from concurrent writers.

Fsync Strategies

Tune the durability-performance trade-off with buffered writing, periodic background flushing, or synchronous fsync on every write operation.

How It Works

Understanding the Bitcask storage and lookup flow.

01

The Append-Only Write Path

When a client writes a key-value pair, the database processes the write sequentially:

  • Create Record: Encapsulates data into a binary entry with CRC32, timestamp, TTL, key size, and value size.
  • Append to Log: Writes the serialized entry directly to the tail of the current Active Segment.
  • Update Index: Inserts a reference mapping the key to the new file ID, offset, and size in the in-memory HashTable.

02

The Single-Seek Read Path

Lookup performs at maximum speed since the location of every key is always in memory:

  • O(1) Search: Checks the HashTable index map. If the key doesn't exist, we immediately return Not Found (no disk read needed!).
  • Verify TTL: Checks if the key has expired. If so, treats it as deleted.
  • Single Disk Seek: Fetches the record from the stored File ID at the precise Offset in a single disk seek.

03

Garbage Compaction

To prevent infinite log growth, a background compaction worker cleans up dead logs:

  • Scan Logs: Iterates over all inactive segments on disk.
  • Filter Dead Entries: Skips records that are deleted, expired, or have been updated by newer writes.
  • Merge Segment: Rewrites remaining live keys into compressed active segments and swaps them atomically.

Compilation & Usage

Quickly build and run the database and CLI on your local macOS or Linux environment.

1. Build Binaries

Compile the server daemon and the CLI interactive program:

# Build server and client CLI go build -o bin/lagerkvd ./cmd/lagerkvd go build -o bin/lagerkv ./cmd/lagerkv-cli

2. Start HTTP Server

Run the storage engine server (by default binds to port 8080 and writes to `data/`):

# Start the background server ./bin/lagerkvd

3. Use CLI Client

Interact with the database using the compiled client CLI:

# Set a key-value with 60 seconds TTL ./bin/lagerkv set username saipraveen --ttl 60s # Get the value ./bin/lagerkv get username # List all active keys ./bin/lagerkv list # View database engine statistics ./bin/lagerkv stats
